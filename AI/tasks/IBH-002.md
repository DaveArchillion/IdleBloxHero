## Objective

Create the first scalable, client-readable, data-driven definition foundation for Idle Blox Hero.

This task establishes the static definition layer and a centralized read-only Data Registry boundary. It must remain independent from runtime player/entity state and must not implement gameplay systems.

## Scope

### In Scope

- Create `src/Shared/Data` as the canonical location for static game definitions.
- Establish the initial definition category structure needed by the core game.
- Create small, explicit definition modules for the first minimal set of data.
- Create a centralized read-only Data Registry module that resolves definitions by `DefinitionId`.
- Define deterministic behavior for unknown `DefinitionId` lookups.
- Establish shared types/contracts needed by the registry without introducing unnecessary abstraction.
- Keep all static definitions safe for client consumption.
- Preserve the existing IBH-001 server/client bootstrap behavior.

### Out of Scope

- Combat
- Hero runtime entities
- Enemy runtime entities
- Player profiles
- DataStore persistence
- Inventory ownership/state
- Equipment runtime state
- Chest opening
- Loot rolls
- Economy
- Marketplace
- Monetization
- UI systems
- External frameworks or packages

## Required Definition Categories

Create the canonical folder boundaries for:

- Heroes
- Enemies
- Equipment
- Accessories
- Materials
- Consumables
- Chests
- Rarities
- Maps

The folders may initially contain only the minimum definitions required for registry verification. Do not generate a large content catalog in this task.

## Definition Rules

- Static definition identifier: `DefinitionId`.
- Runtime entity identifier: `EntityId`.
- Do not use `EntityId` inside static definition records.
- Definitions must describe static configuration, not mutable runtime state.
- Do not store player ownership in definitions.
- Do not store current HP, current XP, cooldown state, or runtime inventory state in definitions.
- Definitions must be explicit Luau tables/modules.
- Avoid metatable-heavy or reflection-heavy designs.
- Avoid inheritance hierarchies.
- Avoid God modules.
- Avoid circular dependencies.

## Registry Contract

Provide a single read-only registry boundary accessible from Shared code.

The registry must support at minimum:

- resolve a known definition by `DefinitionId`.
- return a deterministic failure result for an unknown `DefinitionId`.
- prevent accidental mutation of registered definition tables where practical.
- avoid exposing internal registry implementation details to callers.

Choose a simple API that is easy for future AI agents to understand and extend.

## Initial Definitions

Create the smallest useful verification dataset, such as:

- one Hero definition
- one Enemy definition
- one Rarity definition

The exact identifiers and fields should be selected consistently with the project rules and documented in the implementation report.

Do not create a complete roster or item catalog yet.

## Architecture Constraints

- Shared definitions live under `ReplicatedStorage.Shared.Data` through Rojo mapping.
- Server code may consume Shared definitions.
- Client code may read Shared definitions for presentation/UI.
- Shared definitions must not depend on ServerScriptService modules.
- Shared definition modules must not access DataStoreService, Players, or runtime services.
- Registry must be deterministic and side-effect free during normal lookup.
- No gameplay behavior belongs in the registry.
- Keep dependencies one-directional and obvious.

## Expected File Shape

Use a structure similar to:

```text
src/
└── Shared/
    ├── Bootstrap.lua
    └── Data/
        ├── Heroes/
        ├── Enemies/
        ├── Equipment/
        ├── Accessories/
        ├── Materials/
        ├── Consumables/
        ├── Chests/
        ├── Rarities/
        ├── Maps/
        └── DataRegistry.lua
```

The final structure may be improved slightly when justified, but do not introduce unrelated architecture.
